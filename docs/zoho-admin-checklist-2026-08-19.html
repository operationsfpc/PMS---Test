Zoho CRM → PMS Webhook: Integration Checklist

FACE Prep Campus — Placement Management System  ·  19 Aug 2026  ·  for the Zoho CRM administrator  ·  based on the current “Send Deals to PMS” webhook + “CRM Deals x PMS” workflow rule
What already looks good: Deals module, POST with form-data body, the snake_case parameter names, sourcing from Accounts / Contacts / Deals, and the fixed mm-dd-yyyy date format. Please keep all of that as is.
One rule governs everything below: the PMS validates every payload against the same rules its own form uses, and it refuses rather than converts. A picklist value that is not an exact match, or a missing required field, means the whole Deal is refused and lands as a draft for the AE to redo. So exact values matter more than anything else on this list.

1  Webhook configuration changes

✔ItemWhat to do
☐Add the Deal record IDAdd parameter zoho_record_id = Deal Id. This is how the PMS de-duplicates retries and how it fetches the JD attachment. Without it the integration cannot work.
☐Add the Deal owner’s emailAdd parameter owner_email = Deal Owner → Email. The PMS matches it to the Account Executive’s PMS login. No match → the Deal is refused.
☐Authorization headerCurrently “General” with no header. Before the real URL goes in, add a custom header (name and secret value will be provided) so only Zoho can call the endpoint.
☐Workflow trigger condition“Execute On: Modified” fires on every edit, including half-filled Deals. Change to fire once, deliberately — e.g. when a Stage / picklist becomes “Submit to PMS”. Re-fires are tolerated (de-duplicated) but create noise.
☐Replace the test URLwebhook.site/… is fine for testing. The production URL (a Supabase Edge Function) will be provided together with the auth header secret.

5  The Job Description attachment

  • ☐  The JD is attached to the Deal record itself as a PDF, maximum 5 MB, before submission. The PMS pulls it via the Zoho API using the record ID.
  • ☐  If several files are attached, the JD should be the one whose filename contains “JD” — please agree a naming convention with the AE team (e.g. <Company>-JD.pdf).

6  API access (for pulling the JD + verification)

  • ☐  Create a Self Client in the Zoho API Console (accounts.zoho.in — the .in data centre) and share the Client ID, Client Secret and a grant token for scopes: ZohoCRM.modules.deals.READ, ZohoCRM.Attachments.READ, ZohoCRM.users.READ.
  • ☐  Hand the credentials over directly (not by chat/email in plain text) — they will be stored as server secrets, never in code.

7  What the PMS does with each Deal (for reference)

  • A valid Deal becomes a submitted PIF in the Delivery Head’s approval queue, owned by the AE matched via owner_email.
  • An invalid Deal lands as a draft and the AE is notified in the PMS with the exact problems. The fix is a fresh Deal submission from Zoho — drafts are not edited.
  • Duplicate/retried webhook calls for the same zoho_record_id are ignored — no duplicate drives.
  • Edits in Zoho after submission are not synced. Sent-back PIFs are resubmitted as fresh Deals.
Testing (no sandbox): we will jointly run one end-to-end test using a clearly named dummy Deal (e.g. Account “ZZ-TEST — DO NOT USE”) against the production PMS; everything it creates is removed afterwards. Please keep the webhook.site URL until we hand over the production endpoint + auth secret.
